Hermes Bridge Loop

This patch lets WSA run a minimal live loop: WSA returns the next hook, Hermes executes the actor/subagent call, Hermes writes a callback, and WSA ingests it to update floor state.

Live Loop

Run

--mode hermes-bridge creates pending hook state.

to

Next

WSA returns one hook packet with prompt and terminal command shape.

to

Hermes

Hermes owns real actor/subagent execution.

to

Submit

WSA ingests callback JSON from hermes/callbacks.

What Changed

orchestrator_bridge.py

New minimal bridge engine for next, submit, callback validation, quality gates, floor-state advance, and final review package creation.

orchestrator run

--mode hermes-bridge now creates pending_hooks instead of deterministic local simulated outputs.

orchestrator next

Returns the next Hermes-owned prompt/terminal hook packet as JSON.

orchestrator submit

Accepts completed callback JSON files from the workspace callback directory only, then validates world, session, role, size, uniqueness, and bounded output fields.

Status Model

Status Meaning
waiting_for_hermes WSA has prepared a hook and is waiting for Hermes-owned execution.
running_in_hermes At least one callback has been accepted and more hooks remain.
completed_by_hermes All planned bridge callbacks were ingested and WSA created a review package.
awaiting_author_review No canon mutation happened; the author must approve, hold, or retry.

Boundary

WSA still does not start Docker, Telegram, sockets, provider APIs, or subagents. The bridge loop only makes Hermes execution auditable and resumable through local task/callback files.
